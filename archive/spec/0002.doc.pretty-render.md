## Context

Archive and other docs live in the repository as `.md` and `.adoc` but are read as unified diff text in the review pane. The diff is useful to understand what changed between sides, but for these files the rendered document is the primary reading. Pretty rendering belongs inside the existing diff view, not a second surface to navigate to.

## Scope

* Detecting doc files by extension alone by default inside the existing diff pane, with a per-file toggle back to raw text/diff.
* Hybrid diff awareness for rendered docs: showing the full pretty document with hunk-derived change markers and highlighted fenced code blocks.

## Abstractions

### Doc

A file whose path ends in `.md`, `.adoc`, or `.asciidoc`, detected purely by extension (case-insensitive, no path prefix is special). Rendered as pretty by default inside the existing diff pane.

### Pretty View

The rendered presentation of a Doc inside the diff pane — the full document laid out with Gio/`reef` primitives, with hunk-derived change markers overlaying the diff.

## Mechanics

### Detection

File type is decided from the extension at layout time. The set is `{.md, .adoc, .asciidoc}`; everything else follows the existing path through `internal/ui/diffpane.go:489` `diffRow` / `internal/ui/diffpane.go:776` `drawCode`. Detection is a pure helper (`IsDoc(path string) bool`) used by the row dispatcher. No MIME sniffing, no content sniffing, no config.

#### Frontmatter

Markdown files may start with an optional YAML frontmatter block delimited by `---` on its own line opening and closing. If present, the interior is parsed as YAML into `map[string]any`; parse errors cause the block to be treated as regular content. Keys are rendered in source order as a two-column table (Key, Value) with `reef` text primitives above the document body, values stringified (`%v`). Files without frontmatter render with no table; AsciiDoc files have no frontmatter concept and are not checked for it.

### Rendering

Rendering is in-process with Gio/`reef` only. No webview, no `exec`, no shell-out.

* Markdown via `goldmark` with extensions for tables, strikethrough, autolink and fenced code. The parser produces a block tree that the pretty drawer walks to emit `reef` paragraphs, headings, lists, blockquotes, tables, rules and code blocks.
* AsciiDoc via `github.com/bytesparadise/libasciidoc`. The converter is configured to produce the same block set the markdown path emits so the drawer is shared.

Both paths produce the same layout primitives: heading levels map to `reef` type scale, body text uses the UI font, inline code and fenced blocks use the code font. Links are rendered as coloured text with underline affordance; no navigation is performed.

Fenced code blocks carry an info string (e.g. `go`, `toml`). When non-empty, the block's text is passed through `highlight/highlight.go:72` `File(pathHint, src)` where `pathHint` is `file.<lang>` so `lexers.Match` picks the right lexer, matching the existing diff highlighting (`internal/ui/diffdoc.go:361` `highlightSides`). When the lexer is unknown or the block is too large past `highlight/highlight.go:56` `maxBytes`/`maxLines`, the block renders as plain code. Inline code is not highlighted.

### Hybrid diff awareness

It does not try to align rendered block trees between sides. Instead it renders the full document for the `After` side and overlays change markers derived from the file's diff.

For a doc file, `lightFile` (`internal/ui/diffdoc.go:732`) is extended to fetch both sides via `vcs/vcs.go:61` `FileContent(ctx, spec, path, vcs.After)` and `vcs.FileContent` with `vcs.Before`. The full sources are rendered as above. Separately, the file's `diffparse.File` (`internal/diffparse/parse.go:65` `File`) provides `Hunks` with `OldStart`/`NewStart` line numbers. Hunks are mapped to rendered block ranges by line number: each hunk's `NewStart`/`NewCount` (for adds) and `OldStart`/`OldCount` (for dels) marks a contiguous set of pretty blocks that overlap those lines. Affected blocks get the same visual language the code diff uses — a 2px gutter edge and a paragraph tint (`AddBg`/`DelBg`, `AddGutter`/`DelGutter` from the palette in `reef/scheme.go`) — and a `"+"`/`"−"` marker in the margin. Context blocks have no tint. Blocks that are entirely before or after all hunks render plain.

Because the mapping is by line number, it is stable across renderers and needs no block-level diff. Binary files (`diffparse.File.IsBinary`) and truncated files still show the note path (`internal/ui/diffdoc.go:532` `fileNote`); pretty rendering applies only when the file has text content.

Errors from `FileContent` fall back gracefully: if `After` is unavailable the raw hunk text is rendered; if `Before` is unavailable the overlay shows only additions.

### Toggle and header control

The diff window does not move. Non-doc files are unchanged. For a doc file, `diffRow`/`pairRow` dispatch on type and toggle: when pretty is on they call `drawPretty`, otherwise `drawCode`/`drawCodeWrapped`. Side-by-side and unified wrapping behaviour follow the existing `wrapping()`/`wrapCols` mechanics for code; pretty blocks lay out to the column width and wrap via `reef` text wrapping.

The toggle lives in the file header row (`internal/ui/diffpane.go:634` `fileHeadRow`), beside the existing `WHOLE FILE  ⇧E` control. It reads `PRETTY` when the file is in pretty mode (muted when not) and `RAW` (or `DIFF`) when toggled, mirroring the active/inactive colouring of `SPLIT`/`WRAP` in `internal/ui/diffpane.go:1259` `diffControls`. Clicking flips the per-file toggle and invalidates the file's rows without refetching. Toggle state is held in memory, not persisted, starts on for doc files, and resets on diff reload. Keyboard: `P` toggles the file under the cursor when it is a doc file; otherwise it does nothing.

Comments, gaps and hunk headers: in pretty mode the header row and the toggle remain, but hunk header rows and gap rows are not shown — the hybrid overlay replaces them. Comment anchoring (`internal/ui/diffdoc.go:1249` `fileRefs`, `anchors`/`covers`) continues to work because rows still carry `Line.OldNum`/`NewNum` for the marked blocks; a draft or note whose anchor line falls inside a tinted block appears under that block.
